# 架构与设计

> 这份文档只讲**结构、契约和取舍**。要跑命令看 [OPERATIONS.md](OPERATIONS.md)，
> 要查参数看 [CONFIG.md](CONFIG.md)，踩坑记录看 [NOTES.md](NOTES.md)。

## 零、先搞清楚：这里是「检索」，不是「生成」

本模块只做 RAG 的**左半边** —— 把资料找出来，**不写答案**。

```
用户问题
   │
   ├─────────── 左半边：本模块（knowledge-mcp）───────────┐
   │  问题 → bge 编码 → Chroma 找相似块 → 混合检索融合      │
   │        → 按小节去重 → top_k                          │
   └────────────────────────┬────────────────────────────┘
                            ▼
            prompt = "只依据以下资料回答" + 资料 + 问题
                            │
                            ▼
                右半边：LLM（chat-service / API）
                            │
                            ▼
            "每 60 秒一轮 [comic-scheduler/README.md:42]"
```

### 检索 vs 生成：形状像，性质不同

| | LLM 对话（生成） | 本模块（检索） |
|---|---|---|
| 计算性质 | **生成**：逐 token 自回归，写一个字算一次 | **查找**：一次编码 + 一次比较，算完就结束 |
| 知识在哪 | 参数里（训练时压进去的） | 文档里（随时可改） |
| 可追溯 | ❌ 说不清"这句从哪学的" | ✅ 能给到「第几行第几句」 |
| 会编吗 | ✅ 会幻觉 | ❌ 只返回原文切片 |
| 延迟 | 秒级 | 毫秒级 |
| 更新知识 | 重新训练 / 微调 | 改文档 + 重建索引（约 35 秒） |
| 靠什么跑 | vLLM / SGLang 这类**推理框架**（显存、批处理、并行） | 向量库（Chroma）+ 一个 **ONNX 编码器** |

### 三个容易混的概念

| 概念 | 是什么 | 本项目的例子 |
|---|---|---|
| **模型** | 网络结构 + 训练好的权重文件 | `bge-small-zh-v1.5`（约 95 MB，512 维） |
| **推理框架** | 跑模型的引擎：算子、内存、硬件调度 | `fastembed`（底层 ONNX Runtime） |
| **向量库** | 存向量 + 做最近邻查找 | Chroma（HNSW，余弦） |

> 换**模型** = 换向量空间 → **必须重建索引**；换**框架**只影响速度，不用重建。

## 一、数据流

```
              ┌──────────── 建索引（离线，改文档才跑）────────────┐
仓库文档 ──┐  │                                                  │
schema/API ─┼─→ corpus 加载 ─→ 按标题树切 chunk ─→ 向量化 ─→ Chroma │
用户资料 ──┘  │  (external)      (双文本)                      │   │
              └──────────────────────────────────────────────────┘
                                    │
              ┌──────────── 检索（在线，每次查询）───────────────┐
查询 ─────────┴─→ ┌ 向量：余弦 + 阈值                              │
                    └ BM25：词面命中（倒排索引，内存）           │
                       ↓                                        │
                    RRF 按名次融合 ─→ 按小节去重 ─→ top_k 命中      │
                       ↓                                        │
                    read_knowledge 按 doc_id 回读小节全文          │
              └──────────────────────────────────────────────────┘
```

两段是**解耦**的：检索时 BM25 索引从 Chroma 现读文档现场构建（几十毫秒），
不需要第二份持久化索引；向量集合则要显式重建。

## 三、切分

### 为什么按标题树切，而不是按字符数

一个 `chunk_size=500` 走天下会把 FAQ 从小节中间截断 —— 检索到半截语义，模型看不懂。
标题层级是**作者已经标好的语义边界**，优先用它；只有单节太长时才退化到按段落/句号切。

### 硬约束：embedding 模型的 512 token

`bge-small-zh-v1.5` 的 `max_position_embeddings = 512`，中文 1 字约 1 token。
**超长的后半段会被 tokenizer 静默截断**（不报错），表现为"文档里明明写了，检索就是找不到"。

| 参数 | 值 | 说明 |
|---|---|---|
| 目标 chunk | 300–400 中文字符 | 留足余量 |
| 硬上限 | 500 字符 | |
| token 硬上限 | 480 | 给标题与特殊 token 留余量 |
| 最小 chunk | 120 字符 | 更小的与相邻小节合并 |
| 长段落重叠 | 50 字符 | 仅在被强制切开长文本时 |

### 切分规则

1. 按 H1/H2/H3 标题树切，每个 chunk 带 `heading_path`（如 `部署 / 端口与反代`）；
2. **代码块、表格是原子块**，不从中间切；表格超长时按行切并**重复表头**；
3. 单块代码超过 500 字时整块保留（半截代码比长代码更糟），接受 token 超限；
4. 切完再用 tokenizer 复核 token 数，超限的继续拆；
5. 每个 chunk 记录 `parent_start` / `parent_end`，供回读整节时定位。

### 分块方式：段落 → 句子 → 装箱

一个「小节」通常还会被切成多个**检索单元（chunk）**，流程是三步：

```
① 按空行分段（_split_fenced_blocks）  表格 / 代码块是原子块，其余是普通段落
② 超长段落再切（_split_block）
③ 所有片段进同一个池子，装箱成 ≤500 的块（split_body）
```

> 第 ③ 步是**跨段落装箱**：短段会和相邻段拼成一块，不是"一段一块"。

#### 第 ② 步用 LangChain 的递归切分（`CHUNKER_VERSION = 4`）

`_split_text` 直接调 `RecursiveCharacterTextSplitter`（与 chat-service 同一套算法，
`langchain-text-splitters` 已在同一 venv 里），关键是**分隔符的顺序**：

```python
["\n\n", "。", "！", "？", "；", "\n", " ", ""]
#  段落   句子（标点）        软换行  空格  字符
```

**⚠️ 句号必须排在 `\n` 前面。** 中文文档普遍按 60 字手工折行，**换行不是语义边界**；
把 `\n` 排在前面会让切点落在半句话中间。

递归只在"单个片段 ≥ 上限"时发生，所以每一行都短于 500 时，切点会停在**句子边界**。

实测（`comic-scheduler/README.md › 每一轮都进任务表`，其中一段 506 字）：

| 分隔符顺序 | 结果 | 末块 |
|---|---|---|
| `\n` 优先（v3，按行累加） | `[467, 36]` | 「`Duplicate entry`，且它的收尾会覆盖第一轮的行。」❌ |
| 句子优先（v4） | `[346, 159]` | 完整句子 ✅ |

> 用 LangChain 默认分隔符跑同一段，结果也是 `[467, 36]` —— **问题不在实现，
> 在"把换行当分隔符"这件事本身**。

#### 各类内容的切法

| 内容类型 | 切法 | 理由 |
|---|---|---|
| 普通文本 | 段落 ≤500 整段保留；>500 走上面的递归切分 | 切点落在语义边界，且保住向量完整性 |
| 表格 | 按行切 + **每块重复表头** | 没有表头的行看不懂 |
| 代码块 | **整块保留，宁超 500** | 半截代码比长代码更糟 |
| 尾块 | 暂不合并（见下） | 真残余很少，合并会误伤合法短块 |

**为什么不合并短尾块**：全库碎块里，真正的"句子被切断"只有 9 个（v4 后 6 个），
其余是本来就短的完整内容（短段落、表格行、单句小节）。为 6 个真残余引入合并逻辑，
会误伤那批合法短块。真要彻底消除，正确做法是"按块数均分"，而不是把它们并进上一块。

#### 为什么不是"所有内容都整块保留"

因为"保留"保的是**块里的文字**，保不住**它参与语义检索的资格** ——
`bge` 的窗口是 512 token，超窗口部分会被静默截断。

实测全库 484 个小节：

```
超过 512 token        76 节（15.7%）
不进向量的字数        约 59,159 字（占全库 22.8%）
最长的一节            9,529 字 / 5,935 token（约 91% 不进向量）
```

**接近四分之一的语料会退化成"只能字面命中、无法语义检索"**。所以只有代码块
值得冒这个险；普通文本必须切。

> 改这一层要动索引契约：`CHUNKER_VERSION` 加一 → 集合名随之变化 → 重建索引 →
> **重跑评估**（块变了，向量与 BM25 都会变，Recall / MRR 必须重新确认）。

### 双文本契约：检索文本 ≠ 展示文本

每条 `Document` 存两份文字，这是本模块最重要的一个设计：

| 字段 | 内容 | 用途 |
|---|---|---|
| `page_content` | FAQ：标题 + 正文首句<br>漫画：书名 + 作者 + 标签 + 简介 | **只拿去算向量与 BM25** |
| `metadata["display"]` | 完整原文 | **只拿去拼上下文 / 回读** |

**为什么不合成一份**：向量是整段文字的平均值。用户问句往往只有 4~6 字，
拿去跟 150 字的完整正文比，相似度会被稀释到阈值以下（实测：合成一份 0.489，
分离后 0.56）。**模型读到的内容不变，变的只是"拿去比对的那段文字"。**

> 改 `page_content` 的拼法必须把 `CHUNKER_VERSION` 加一，否则会继续用旧向量 ——
> 症状是"代码明明改了、效果一点没变"，而且不报错。

## 四、分词（词项层）

两处依赖"把一句话切成词"：**界面命中词高亮**和 **BM25 召回**。
两处必须同一套切法，所以统一收在 `tokenizer.py`，可切三个后端：

| 后端 | 切法 | 特点 |
|---|---|---|
| `mixed`（默认） | 标识符整体保留 + 部件展开，中文段交 jieba | 中英兼顾 |
| `jieba` | 词典 + DAG + 最大概率路径 + HMM 未登录词 | 中文好，英文标识符会被拆碎 |
| `bigram` | 英文/数字整词 + 中文两字滑窗 | 零依赖，中文有跨词碎片噪音 |

**为什么默认 `mixed`**：中文两字词在 bigram 与词典切分下**完全等价**，差异只出现在
三字以上词和虚词碎片上；而英文/数字标识符（`require_admin`、`X-Service-Token`）
恰好是 bigram 保整体、jieba 拆碎。分流后两边优点都拿到：

```
require_admin 是哪个装饰器 → require_admin, require, admin, 哪个, 装饰
图床地址是什么            → 图床, 地址, 什么        （不会产生 是什 这种假词）
```

**用户词典**（`src/comic_rag_mcp/terms.txt`）：jieba 默认词典不认识
「判重 / 图床 / 管理台 / 按需导入」这类项目术语，不配词典时它们会被切碎，
**上 jieba 反而比 bigram 更差**。新增模块术语要一并补进来。

> ⚠️ **换分词器 = 换打分刻度**：BM25 的分数是逐词求和，分词一变，
> 加数个数、词频口径、文档长度基准、IDF 分布全变。
> 换后端后必须重跑评估集并重标权重，与换 embedding 模型是同一类问题。

## 五、检索：双路 + RRF

### 三种模式的中文名

界面、命令行、文档**统一用中文称呼**；英文键只出现在代码、配置和接口参数里：

| 中文名 | 键 | 走哪几路 | `score` 的含义 |
|---|---|---|---|
| **语义检索** | `vector` | 只看向量 | 余弦（0~1） |
| **字面检索** | `lexical` | 只用 BM25 | BM25 原始分（0~20+） |
| **混合检索**（默认） | `hybrid` | 向量 + BM25，RRF 融合 | RRF 分（≈0.19，量级随 k/权重重标） |

命令行与接口都**接受中文**：`cli search --mode 语义检索`、`?mode=混合`，
内部由 `retriever.normalize_mode()` 归一。

```
查询
 ├─ 向量路：Chroma 余弦 → min_score 过滤 → 排名次
 └─ BM25 路：倒排索引打分 → 排名次
      ↓
   RRF = Σ weight_i / (k + 名次_i)      k=3，权重 语义 0.75 / 字面 0.25
      ↓
   按 (path, heading_path) 去重（同一小节只留最高分）
      ↓
   top_k
```

### 语义那一路的分数 = 余弦 + 一项"模块加成"

语义分的主体就是 `as_retriever()` 返回的余弦；额外只保留**一项**很小的加成：

```
语义分 = 余弦 + 模块加成
模块加成 = +0.06  当查询意图命中的模块 == 命中块的模块
         = +0.03  当查询意图是 api、命中块是表结构（schema）
         = 0      其余情况
```

查询意图靠一张关键词表判断（`爬虫/采集 → crawler`、`定时/cron → scheduler`、
`接口/鉴权/token → api` …），见 `retriever._MODULE_HINTS`。

**为什么只留这一项**（2026-11 实测，20 条黄金题，语义检索）：

| 加成策略 | Recall@5 | MRR | nDCG | Top-1 |
|---|---|---|---|---|
| 不加任何加成 | 18/20 | 0.810 | 0.851 | 75% |
| 只加标题（+0.12） | 17/20 | 0.775 | 0.813 | 70% |
| 只加正文（+0.08） | 17/20 | 0.767 | 0.825 | 70% |
| **只加模块（默认）** | **20/20** | **0.950** | **0.982** | **90%** |
| 三项全加（旧版） | 20/20 | 0.825 | 0.944 | 70% |

标题/正文加成会引入噪音（"讲这个话题的笔记"被顶上去）；模块加成是**便宜的先验**：
它只在问题里出现模块线索时生效，其余查询完全退化成纯余弦。

开关是 `COMIC_RAG_BOOST`（`module` / `none` / `heading` / `body` / `all`），
可随时关掉做 A/B。

⚠️ 语义分只属于**语义那一路**：**混合检索**下 `score` 是 RRF 分（≈0.16），
余弦决定的是**它在语义榜排第几**，不是最终的 `score`。

### 混合那一路：k 与权重决定"谁赢"

`EnsembleRetriever` 的排序是 `Σ weight_i / (k + 名次_i)`，两个旋钮都**真的改变排序**
（早期文档写"k 只影响量级"是错的，已更正）：

| 参数 | 默认 | 作用 |
|---|---|---|
| `COMIC_KB_RRF_K` | **3** | 放大名次差距；k=60 时"两路都靠后"会压过"单路第一" |
| `COMIC_KB_RRF_WEIGHTS` | **0.75,0.25** | 语义:字面；等权会让字面噪音（自文档污染）抢走第一 |

**设计意图**（排序偏好，由 `tests/test_fusion.py::RankingPreferenceTest` 守卫）：

```
两路第一 > 一路第一+一路靠后 > 单路语义第一 > 单路字面第一 > 两路靠后 > 单路靠后
```

实测（20 条黄金题）：`k=60` + 等权 → 混合 Top-1 **65%**；`k=3` + `0.75/0.25` →
**90%**（MRR 0.950、nDCG 0.982，与纯语义持平，但保留了字面兜底）。

### 为什么要两条路

不是精度高低，是**能力类型不同**：

- 向量回答「哪一条最像」，擅长口语、错字；
- 词面回答「哪几条含这些词」，擅长型号、报错码、函数名、专有名词。

实测：查 `X-Service-Token` 时向量 top-10 一条都不对（它把"鉴权相关"的 openapi 排前面），
BM25 第 1 名即正确。反过来查「某术语 + 是什么」这类疑问句时，BM25 会把 NOTES 的
「条目模板」章节捞上来（它们含"是什么"），向量那路没这个毛病。

### 为什么按名次融合，不按分数相加

向量分是 0~1 余弦，BM25 是**无上界实数**（实测 0.4~20），两者不可比。
直接相加，量级大的那一路永远赢，等于另一路白做。RRF 只看名次，天然免疫量纲问题。

### 三个必须知道的语义

1. **`score` 的含义随模式变化**：**语义检索**是余弦（0~1），**混合检索**是 RRF 分
   （`weight/(k+名次)` 累加，默认 `k=3`、权重 `0.75/0.25`，量级约 0.1~0.2）。
   要判断"像不像"请读 `vector_score`。
2. **`min_score` 只作用在语义那一路**。融合后分数量级完全不同，拿 0.45 卡会一条不剩。
3. **RRF 只合并、不裁决**：它给不出"哪条更相关"的判断，只按名次累加。两路各自
   第一名的两条，**在等权时融合分完全相同**（默认权重不等，语义第一会胜出）。
   真正要"读内容重新判断"得靠重排（rerank），见 [NOTES.md](NOTES.md) 2.7。
4. **`k` 与权重都会改变排序**（早期文档写"`RRF_K` 只影响量级"是错的，已更正）：
   `k` 越大，"两路都出现"越值钱，k=60 时"两路都靠后"能压过"单路第一"。

## 六、索引与集合指纹

- 目录：`crawler-service/data/project_rag`（可用 `COMIC_RAG_INDEX_DIR` 覆盖）
- 集合：`project_kb_<backend:model:dim:chunkN 的短哈希>`
- 距离度量：**必须 cosine**。Chroma 默认 L2，`langchain-chroma` 用 `1 - distance` 换算，
  于是 distance>1 时分数变负数（实测 -0.13 / -0.22）；且 `collection_metadata`
  **只在集合首次创建时生效**，所以重建时必须先 `delete_collection()` 再重开。

**集合名带配置指纹**，是为了把"换模型必须重建索引"这条规则变成工程兜底：
换个 embedding 模型还往同一个集合里写，维度不同的直接报错，**维度碰巧相同的更糟 ——
向量不在同一个语义空间，检索结果是噪声，而且不报错**。带指纹后改配置自动落到新集合，
旧索引保留。

- `manifest.json`：每个文件的 sha1 / 大小 / chunk 数、embedding 参数、切分版本、构建时间
- **过期检测**：对比当前文件与 manifest，输出 `changed / new / missing` 三个列表

## 七、回读契约：`read_mode`

| 值 | 适用 | 行为 |
|---|---|---|
| `lines` | Markdown / SQL（文件真实存在且是纯文本） | 按 `parent_start/end` 回读**原文件行号区间**，拿到整节 |
| `chunk` | OpenAPI / Word / Excel（没有稳定行号） | 只返回命中的那条 chunk 正文 |

Word / Excel **不做 section 级回读**是有意接受的限制：原始文件是二进制，
Word 转出的中间 Markdown 在磁盘上并不存在，没有行号可回。

命中结果按 `(path, heading_path)` 去重：一个长小节会切成多个 chunk，
`read` 反正会回读整节，重复 chunk 只会挤占 `top_k`。

### 三份文本，别混

| 文本 | 是什么 | 谁在用 |
|---|---|---|
| **原文小节** | 磁盘上 `parent_start..parent_end` 的原始 Markdown | 回读（`/api/section`、`read_knowledge`） |
| **chunk 正文** | 小节被切出来的一块（`page_content` 去掉 `heading_path` 前缀） | 卡片摘要、算向量/BM25 的原料 |
| **snippet** | chunk 正文压成一行、截断 300 字 | 列表快速扫 |

**块与整节的关系**：块是整节的切片，但**不是无缝平铺** —— 每块会被 `strip()` 掉首尾空白，
所以块之间会留下空行，小节标题行也不属于任何块。调试界面会显示
「覆盖 709 / 728 字 · 缝隙 19 字」，把这点差异**量化出来**，而不是假装严丝合缝。

## 八、message 子索引

message 表**不直连数据库**，而是由 api 的只读接口暴露：

```
GET /api/internal/knowledge/messages?cursor=&limit=
X-Service-Token: <HMAC>
```

- 按 `id` 升序返回**全量**行（不做收件范围过滤）；
- 消息表是**追加式**（没有 `updated_at`），所以增量游标就是 `id > last_id`；
- 因为含定向/管理员消息，**只认服务令牌、不认用户 JWT**；
- 集合 `project_kb_message_*` **与文档集合分开**：消息增量刷新不该触发文档全量重建。

## 九、进程与权限边界

| 关注点 | 做法 |
|---|---|
| 对外形态 | MCP stdio，不监听端口；只有本机 Agent 能拉起 |
| 写能力 | 无。只读 Chroma、只 GET 内部接口 |
| 生成 | 不调用对话模型（那是 chat-service 的职责） |
| 失败语义 | 索引缺失/为空/版本不匹配时抛 `ToolError`，**不返回空 hits 假装"没有资料"** |
| 依赖边界 | 复用 chat-service 的 embedding 与 Chroma 技术栈，但与它的索引互不干扰 |
