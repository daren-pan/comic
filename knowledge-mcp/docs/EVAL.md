# 检索评测

> **只放评测**：题集、指标、成绩、怎么加题。设计见 [ARCHITECTURE.md](ARCHITECTURE.md)，
> 跑测的命令见 [OPERATIONS.md](OPERATIONS.md)，踩坑见 [NOTES.md](NOTES.md)。

**方法**：20 条项目问题，`top_k=5`；命中期望文件中的任意一个即算通过。
只看"文档有没有被召回"，不判断最终答案质量。

## 指标定义

| 指标 | 算法 | 回答什么问题 |
|---|---|---|
| **Recall@k** | 前 k 条里有没有正确文档（0/1） | 能不能找到 |
| **MRR@k** | 平均 `1 / 首个正确命中的名次`（没命中记 0） | 找到的排第几 |
| **nDCG@k** | `Σ gain_i / log2(i+1)`，二值增益，理想 DCG 取 1 | 排得够不够靠前 |
| **Top-1** | 第 1 名正确的比例 | 首条能不能直接用 |

三点约定：

1. **只看名次，不看分数**。三种模式的分数不可比（余弦 0~1 / BM25 无上界 / RRF ≈0.19），
   依赖分值的指标会让 A/B 在错误的尺子上比较；
2. **期望集合是"任一即可"**，所以 nDCG 的理想 DCG 取 1.0（正确文档排第一即满分），
   不按 `len(expect)` 算 —— 那会假设"所有候选都要找到"，与标注语义不符；
3. **Recall 会掩盖排名退化**：`同源判重键` 从第 2 掉到第 4 时 Recall 依然算过，
   MRR 会从 0.50 掉到 0.25。**改检索必须同时看 MRR / nDCG。**

运行：

```bash
# 汇总（默认 hybrid）
bash scripts/dev.sh knowledge-eval

# 逐题明细：每条命中 + 名次 + 该题得分（人工核对用）
crawler-service/.venv/Scripts/python.exe -m comic_rag_mcp.cli eval --mode hybrid --detail

# 存基线 / 接脚本
... cli eval --mode vector --json > baseline.json
```

单题调试用 `search --explain`：直接看到每条命中的分数构成、来自哪一路、被哪几个词命中。

## 结论

- 第一版“能查到”已经达标：20 条全部在 top 5 内；
- 但 Recall@5 掩盖了 **top-1 排序**问题：#05 把“具体源站 API”排到了
  “怎么新增源”前面；#02/#06/#10/#11 路径对但小节不是最贴切；
- 后续应补 **MRR / top-1 accuracy / 答案正确性**，不要只看 Recall@5；
- 如果继续调，优先调“查询意图 → 模块/文档类型”的加权，而不是继续加大 chunk。

## 当前基线（2026-11-07，`mixed` 分词 + 切分 v4 + 20 条题）

| 模式 | Recall@5 | MRR@5 | nDCG@5 | Top-1 |
|---|---|---|---|---|
| **语义检索**（`vector`） | **100%** (20/20) | **0.950** | **0.982** | **90%** (18/20) |
| **字面检索**（`lexical`） | 90% (18/20) | 0.710 | 0.817 | 60% (12/20) |
| **混合检索**（`hybrid`，默认） | **100%** (20/20) | **0.950** | **0.982** | **90%** (18/20) |

> 数字有 ±0.01 的浮动：文档本身也在语料里，改文档就会轻微改变检索结果。
> **做 A/B 时保持文档不变**，否则比的是"文档 + 代码"的混合效果。

**✅ 2026-11-08 更新：混合检索的排序短板已消除。**

- RRF 从 `k=60` + 等权，改成 `k=3` + `0.75/0.25`（`COMIC_KB_RRF_K` / `_WEIGHTS`）；
- 混合 Top-1 **65% → 90%**，MRR **0.781 → 0.950**，nDCG **0.919 → 0.982**，与纯语义持平；
- 原因：k 大时"两路都靠后"会赢过"单路第一"，字面那路的噪音（自文档污染）因此抢到前排；
  调小 k 并给语义更高权重后，"单路语义第一"重新有分量；
- 剩下的 2 条 top-1 失败来自**自文档污染**（NOTES 里引用题目原句的段落），
  不是融合策略问题 —— 见 [NOTES.md](NOTES.md) 2.6 / 2.7。

## 后续用例

建议按模块补到 40~50 条，尤其：

- 部署排障（容器健康检查、端口冲突、volume）；
- 认证边界（`require_admin` vs `require_superadmin`、service token）；
- 采集源新增（adapter 契约、fixtures、注册）；
- 数据库迁移（0001~0010 的语义、回滚）；
- 前端两套构建（H5 / 小程序、`src/utils/*` 兼容层）。
