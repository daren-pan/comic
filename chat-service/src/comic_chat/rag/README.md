# RAG 内核（`comic_chat/rag`）

用**站内真实数据**跑通 LangChain + RAG 的完整链路，每一步的中间结果都能看到。

这套代码既是**生产客服的内核**（`comic-chat` 容器里跑的就是它），也能脱离服务单独用命令行
研究和调参 —— 两边调的是同一个 `chain.ask()`，所以不会出现「实验室效果好、上线效果差」。

## 三十秒上手

```bash
# 在项目根目录
PY=crawler-service/.venv/Scripts/python.exe

# 0. 复制配置模板，填 COMIC_LLM_API_KEY（只 ask 需要，index / search 不用）
cp chat-service/src/comic_chat/rag/.env.example chat-service/src/comic_chat/rag/.env

$PY -m comic_chat.cli doctor                    # 1. 看配置：用哪个向量后端
$PY -m comic_chat.cli index                     # 2. 建索引（64 个文档 → 64 条向量）
$PY -m comic_chat.cli search "图裂了怎么办"       # 3. 只看检索命中（不花钱）
$PY -m comic_chat.cli ask "图裂了怎么办"          # 4. 完整问答（需要对话模型 key）
```

`search` 和 `ask` 的差别就是「检索」和「生成」两段。**调试时永远先用 `search`。**

### 两种跑法

```bash
# 本地（两个进程：客服 + api 转发）
bash scripts/dev.sh up chat     # :8001
bash scripts/dev.sh up api      # :8000

# 容器（索引由容器启动时自动检查，空则建一次）
bash deploy/up.sh
```

手动装依赖时注意两点：

1. `pip install -r chat-service/requirements.txt`（**别再装到 api 的环境里**）
2. `HF_ENDPOINT=https://hf-mirror.com` 别删，否则首次建索引报
   `Could not load model ... from any source`（国内直连 HuggingFace 基本不通）

容器里这两件事都由 `deploy/chat/Dockerfile` 处理：装 wheel + **构建期预热模型**
（不预热的话第一次提问要现下 90MB，卡 30 秒，而健康检查还是通的）。

## 七步链路 → 对应代码

| # | 步骤 | 干什么 | 代码位置 |
|---|---|---|---|
| ① | 加载 | MySQL 的 54 部作品 + FAQ 的 10 节 → `Document` | `documents.py` |
| ② | 切分 | FAQ 按 `##` 切开；作品不切。每条再拆「检索文本 / 展示文本」 | `documents.py` |
| ③ | 向量化 | **只有检索文本**被转成 512/1024 个浮点数 | `embeddings.py` |
| ④ | 存储 | 写进 Chroma，落盘到 `COMIC_CHAT_INDEX_DIR`（默认 `DATA_ROOT/rag_lab/`） | `index.py` |
| ⑤ | 检索 | **双路**：结构化精确匹配 + 向量语义匹配，合并去重 | `chain.py` / `structured.py` |
| ⑥ | 增强 | 4 条的**完整原文**（`metadata["display"]`）拼进 system prompt | `chain.py` |
| ⑦ | 生成 | 模型读 prompt → 输出答案 | `chain.py` |

## 检索设计：为什么是两条路、两份文本

这一节记录**当前实现的设计依据**，改检索前先读这里，能省掉重复试错。
所有数字都是 2026-10-30 在站内真实数据（10 条 FAQ + 54 部作品）上实测的。

### 一、双路召回：结构化 + 向量，缺一条就有一类问题答不好

```
用户提问
  ├─ ① 结构化（structured.py）  书名/作者/标签 反向包含 → 固定档位分数
  └─ ② 向量（Chroma）          语义最近邻 → 余弦相似度
       ↓
     合并去重（结构化优先）→ 阈值过滤（只作用在向量结果）→ top 4
```

| 查询 | 只有向量 | 加结构化 | 为什么 |
|---|---|---|---|
| 有没有科幻的 | **top4 里 0 条相关** | **4/4 全相关** | 这是**集合筛选**，正确答案是 6 部；向量只返回 1 条最像的 |
| 유산도（韩文作者） | 0.455，答成《HIGH不起来的约会》 | **0.95，准确命中** | `bge-small-zh` 词表里没有韩文 |
| 杜鹃的婚约 | 0.79（top1 还是繁体版） | **1.00，两条都返回** | 精确标题不该被模型打成 0.79 |
| 五十岚正邦的作品 | 0.53 | **0.95** | 作者名比语义更该走精确匹配 |
| 图骗打不开 | 0.61 ✅ | 0.61 ✅（向量那条路） | 结构化**完全无能**，用户问法千变万化 |
| 有个漫画讲高中生找电台主播 | 0.55 ✅ | 0.55 ✅（向量那条路） | 情节描述只能靠语义 |

**核心认识：这不是「精度高低」，是「能力类型」不同。**
向量回答「哪一条最像」，结构化回答「符合某属性的有哪些」。
所以 `structured.match()` 返回空列表是**正常情况**，不代表查不到 —— 交给向量继续找。

落地时的三个约定：

| 约定 | 原因 |
|---|---|
| **反向包含**（`书名 in 提问`） | 用户问句长（「五十岚正邦的作品」8 字）、字段短（「五十岚正邦」5 字），正向匹配几乎永远对不上 |
| **固定档位分数**（1.00/0.95/0.85） | 用户报确切书名时就该 100% 命中，不该被向量打个 0.79 排在别的作品后面 |
| **与索引同生命周期**（`comic_facts()` 缓存） | 由 `build_index()` 统一刷新。若结构化先看到新作品而向量库里还没有，会出现「匹配到却检索不出内容」 |

### 二、文档分离：检索文本 ≠ 展示文本

每条 `Document` 存两份文字：

| 字段 | 内容 | 谁用 |
|---|---|---|
| `page_content` | FAQ：标题 + 正文首句<br>漫画：书名 + 作者 + 标签 + 简介 | **只拿去算向量** |
| `metadata["display"]` | 完整原文（FAQ 整段 / 漫画 8 行） | **只拿去拼 prompt 和界面预览** |

**为什么不能合成一份**：向量是整段文字的平均值。用户问句往往只有 4~6 字
（「要不要钱」），拿去跟 150 字的完整正文比，相似度被稀释到阈值以下 ——
实测 **0.489**，差 0.011 被误杀，回答退化成「站内暂时没有」。
分开之后 **0.56**，稳过阈值。

FAQ 用「标题 + 首句」而不是只留标题：标题管「问的是什么」，首句管「细节词」。

| 提问 | 只留标题 | 标题 + 首句 |
|---|---|---|
| 收藏按钮在哪 | 0.61 | **0.73**（标题里没「按钮」二字，首句里有） |
| 要不要钱 | 0.75 | **0.56**（够用且细节不丢） |

漫画的检索文本去掉 `状态` / `章节数` / `最新话` 三行：它们几乎没有区分度
（每部都有章节数和最新话），却会稀释书名和简介的语义。实测章节类查询只从
0.79 掉到 0.75 —— 书名本身占主语义。
**但简介必须完整**：截断到 60 字会让「有个漫画讲高中生找电台主播」从第 1 名掉到第 2 名。

⚠️ **`comic.category` 已废弃，检索与展示都不用它。** 它是采集侧早期存的原始分类串
（`'爱情, 校园'` 这种多值字符串），权威标签来源只有 `comic_tag` 关联的 `tag` 表。
两边都放会让同一部作品出现两套互相矛盾的题材（旧值不会跟着标签更新）。
`DOC_FORMAT_VERSION` 从 2 升到 3 就是这次改动。

⚠️ **改了 `page_content` 的拼法，必须把 `settings.DOC_FORMAT_VERSION` 加一。**
它算进集合名指纹，保证自动换新集合并重建索引 —— 否则会继续用旧向量，
症状是「代码明明改了效果一点没变」而且**不报错**。

### 三、关键参数与标定依据

| 参数 | 值 | 怎么定出来的 |
|---|---|---|
| `TOP_K` | 4 | 3 条常常不够（答案分散在两节 FAQ 里），8 条以上开始稀释 prompt |
| 阈值 `min_score` | **0.5** | 正例实测 0.54~1.00，无关查询峰值 0.52。0.5 正好卡中间 |
| `fetch_k` | `top_k × 3` | 过滤发生在「取回之后」，只取 4 条会被筛到不够 4 条 |
| 结构化档位 | 1.00 / 0.95 / 0.85 | 标题 > 作者 > 标签（可信度递减） |
| 交集门槛 | ≥ 3 个 2 字片段 | 定 2 会让「短发女孩和猫的故事」误命中《態度冷淡的店員小姐的故事》 |

**换 embedding 模型后阈值要重新标定** —— 分数分布会变（见 `NOTES.md`）。

### 四、被实测否掉的方案（别再试一遍）

| 方案 | 实测结果 | 结论 |
|---|---|---|
| FAQ 只留标题 | 「收藏按钮在哪」0.70 → **0.61** | ❌ 丢细节，用「标题 + 首句」 |
| 截断漫画简介到 60 字 | 情节查询从第 1 名掉到**第 2 名** | ❌ 简介必须完整 |
| FAQ 也改结构化匹配 | 「图骗打不开」「登不上去」**全部无命中** | ❌ 自然语言知识只能靠向量 |
| 混合检索用 BM25 | 字面召回边际价值只有 **1/17**（仅韩文作者） | ⏸ 64 条数据量下不划算；但**反向包含**版本有价值，已并入 `structured.py` |
| 提高阈值到 0.6 清噪音 | 「图裂了怎么办」正确项只有 0.522，会被一起筛掉 | ❌ 绝对阈值上调会误伤 |
| 换更大的 embedding 模型 | 只改文档构造就把正例从 6/8 提到 8/8，**模型一行没动** | ⏸ 瓶颈在文档构造，不在模型 |
| 繁简重复去重 | 《杜鹃的婚约》#13 与《杜鵑的婚約》#12 是两条 | ⏸ **不用去重**：实测模型会主动说「有两条记录，进度分别是…」，信息更全 |

## 四个必须理解的点

**① 切分粒度由数据形态决定，不是一个 `chunk_size` 走天下**
FAQ 有 10 个小节，按 `##` 切；作品简介平均 102 字，**不切**。给短文本套
`RecursiveCharacterTextSplitter(chunk_size=500)` 等于没切，给长篇 FAQ 按字符切会把一节
从中间劈开 —— 检索到半截，模型看不懂。

**② 向量只用于「找」，找到后给模型看的是原文**
`page_content` 已经是「检索专用短文本」，**不能再拿它去回答**。拼 prompt 一律用
`metadata["display"]`（完整原文），否则会把后半段结论丢掉（比如「没绑定邮箱的账号
需要找管理员重置」就在第二句）。永远不要把向量塞进 prompt。

**③ 分数方向别搞反**
`similarity_search_with_relevance_scores()` → **0~1，越大越像**（本项目用这个）
`similarity_search_with_score()` → **距离，越小越近**

**④ 换模型 / 换检索文本构造 都必须重建索引**
不同模型的向量不在同一个语义空间。本项目让集合名带配置指纹
（`comic_kb_<hash>`，含 `DOC_FORMAT_VERSION`），换配置自动落到新集合，**忘了重建也不会串**。

## 三个实验（改一行代码，看结果怎么变）

| 实验 | 怎么改 | 你会看到 |
|---|---|---|
| 切分太碎会怎样 | 给 `load_comic_documents()` 也套上 `RecursiveCharacterTextSplitter(chunk_size=40)` | 「《某作品》作者是谁」检索到的片段里只剩书名没了作者 |
| 阈值的作用 | `search --topk 10`，再把它设成 `min_score=0.6` | 低分噪音（无关漫画简介）被挡住，答案不再跑题 |
| topK 不是越大越好 | `--topk 1` vs `--topk 8` | 1 条常缺信息，8 条开始被无关内容带偏 |

## 三个向量后端

| 后端 | 条件 | 效果 | 用途 |
|---|---|---|---|
| `openai` | 配了 `COMIC_EMBED_API_KEY` | 最好 | 正式效果 |
| `local` | 装了 `fastembed` | 够看 | **默认**，离线免费 |
| `hash` | 都没有 | 只反映字面重合 | 验证链路 |

切换只需改环境变量 + 重建索引，代码不动。

```bash
# 切到云端 embedding（通义百炼，DeepSeek 没有 embedding 接口）
export COMIC_EMBED_API_KEY=sk-xxx
$PY -m comic_chat.cli index     # 集合名会自动变，旧索引保留
```

## 依赖与权限边界

| 关注点 | 做法 |
|---|---|
| 依赖 | 全部收在 `chat-service/` 这个镜像里，**api 镜像不装**（只多一个 httpx） |
| 进程 | 独立容器，崩了只影响客服 —— 主站 `/api/health`、`/api/comics` 照常 200 |
| 鉴权 | 在 api 那层（`/api/chat/*`），本服务不认人、也不该认 |
| 网络 | 不映射宿主端口，只有同一 compose 网络的 api 能访问 |
| 开关 | `COMIC_CHAT_LAB=0` 时 api 不挂载这些路由（请求 404） |
